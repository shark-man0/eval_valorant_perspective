# プレイ評価44ルールの成立状況（Issue #32）

44ルールそれぞれについて、トリガーとなるイベントと必須の状態（Fact）が実動画で観測できるかを、コードから機械的に集計できるようにした。あわせて、外部知識（#96）を使う読み取り器で不足していた入力を増やし、実動画で評価候補が出るルールを増やした。

ここでいう「評価候補」は開発用の観測で、正式なFact・Event・評価ではない（`formal_outputs = 0`）。

## 判定の仕組み

- `config/rule_producer_status_v1.json`：イベント31種・Fact37種ごとに、生成器と成熟度（`none` / `contract` / `development` / `qualified`）を変更前と変更後で記録する。
  - `contract`：生成器はあるが、スキーマと合成テストだけで実録画での観測がない
  - `development`：開発用の経路で実録画から観測している
  - `qualified`：独立した実動画検証に合格（現時点ではゼロ）
- `rules/coverage.py`：ルールの成立度を「トリガーのうち最も成熟したもの」と「必須Factのうち最も弱いもの」の低い方で決める。`allow_unscored` の必須Factも、ないと `unscored` にしかならないので必須として数える。
- `rules/development_readiness.py`：実録画から得た観測列から候補Fact・候補イベントを作り、ルールの述語（eq / in / gt / gte）を満たす回数を数える。

```sh
PYTHONPATH=src python3 scripts/rules/rule_coverage_report.py [--occurrences REPORT.json]
PYTHONPATH=src python3 scripts/rules/rule_readiness_real_video.py --cache ASSETS --out PRIVATE.json CROPS/*.zip
# 1秒ごと（元動画のキーフレーム）。特徴量は extract_second_features.py で作る
PYTHONPATH=src python3 scripts/rules/rule_readiness_seconds.py --features SEC_DIR --out PRIVATE.json
```

- 評価の区分は3つに分ける（`config/producer_evaluation_v1.json`）。
  - 開発評価（development）：露出済みの36試合での目視確認。開発候補（`dev-`、採点対象外）の品質の目安で、資格付けではない。
  - 共通タイムラインからの昇格（promoted_from_shared_timeline）：#164 の昇格器が証拠条件を満たした観測だけを正式Event/Fact（`tl-`）にする。閾値は開発用36試合で較正した運用値で、独立評価ではない。
  - 独立資格付け（independently_qualified）：未露出の独立評価用録画での合格。該当する録画がまだないため0件。
- 正式なFact/Eventへの昇格は #164 の `facts.timeline_promotion` だけが行う。本PRの認識器は共通タイムラインの観測行（`raw["values"]` と確信度）を供給するだけで、別の昇格機構や状態管理を持たない（以前の `rules/qualification.py` は削除した）。

スパイク見出し・得点とタイマーの数字・弾倉の数字には、Riotが単体の画像を配布していない。そこで、開発用録画から作ったテンプレートを、公式画像と同じ非公開キャッシュに置いて使う（リポジトリには入れない）。

- 作成に使えるのはTRAIN分割の21試合だけ。ビルダーはデータセット登録簿と元動画のSHA-256で照合し、TRAIN以外が混ざると止まる（`knowledge/template_lineage.py`）。系譜（登録簿・各録画・切り出しアーカイブのSHA-256）はマニフェストに記録し、読み取り側は系譜のないテンプレートを読み込まない。
- スパイク見出し：目で確認した1サンプルを起点に、一致度0.9以上の切り出しを平均して作る。紛らわしい砂時計表示の平均を陰性テンプレートにして差し引く（2×見出し−砂時計 ≥ 0.68）。TRAINでは砂時計の最高0.673、見出しの最低0.683。表示言語やキー設定に左右されないよう、文字とキー表示は含めない。
- 数字：開発時にTesseractでラベルを付け、数字ごとに中央値をとって作る。アプリ本体はTesseractを使わない。精度は `docs/top_bar_score_timer.md` に、得点（1フレーム 160/160 正答、補完後の時系列 219/221）、タイマー（23/23）を記録した。弾倉の数字は 55/55 正答（値を返した割合 85％）。

本人視点・生存・観戦は、共通タイムラインの書き出しがある試合（10/36）ではタイムラインの SELF かつ ALIVE をそのまま使う。独自の推定で上書きはしない。書き出しがない試合だけ、表示中のアビリティHUDが録画者のエージェントと一致するかで判断する。

### 死亡のRound単位の照合（`rules/recorder_life.py`）

- Roundの正本は共通タイムライン。タイムラインのRound番号（得点とRound段階から求めたもの）でRoundを区切り、開始と終了にはタイムラインの round_start／round_end を使う（`TimelineView.rounds`）。独自の境界で上書きしない。
- 前回、タイムラインのある試合でRoundが細かく分かれすぎていた原因は、タイムラインではなく、round_start が欠けた区間を規則側が5対5への戻りで埋めていたこと。タイムラインの round_start は例えば17Round中7件しかないが、Round番号は全Roundにある。
- 書き出しがない26試合だけ、上部バーの得点から仮のRoundを作り、`provisional_score` と明記する。どちらかのチームの得点が増えた時点を境界とし、開始時刻は直後に5対5へ戻った時点に合わせる。5対5が20秒以上続いた戻り（購入フェーズ）は、得点の読み取りが途切れて見落とした境界として加える。
- 得点の読み取り結果は、共通タイムラインの観測行の形式で渡せるようにした（`docs/top_bar_score_timer.md`）。
- 上部バーで味方5人全員の生存が、候補の時点と次のサンプルの両方で見えている死亡候補は捨てる（Round切り替え時のHUDの入れ替わりによる誤検出）。
- 死亡候補は、タイムライン → キルフィードの本人強調 → 自分のHUDの喪失（タイムラインなしの試合のみ）の順に扱い、8秒以内の同じ死亡は1件にまとめる。
- 1つのRoundの死亡は原則1回とする。2回目は、その間に本人視点の生存がRound途中（生存者が10人未満）で5秒以上続いた場合だけ「復活後の死亡」として残し、それ以外は重複として統合する。秒数で決めるので、1秒間隔と5秒間隔で同じ基準になる。
- HUDの切り替わりによる死亡候補と、キルフィード候補の確認に使う「本人以外の視点」は、3秒以上続いたものに限る（1秒間隔での1フレームの誤読を除く）。
- キルフィードの本人強調があっても、被害者の顔写真が録画者以外のエージェントと判定された項目は、録画者の死亡にしない。
- Round境界の外の候補は捨てる。タイムラインが観戦中としている時点のHUD由来の候補も捨てる。
- 本人強調は録画者自身のキルにも付くため、キルフィード由来の候補は、12秒以内に本人以外の視点が現れた場合だけ死亡として採用する。

### 死亡と復活の判定（1秒経路と5秒経路、36試合）

同じRoundの2回目の死亡は、これまで「間に本人視点が5秒以上続いた」だけで復活後の死亡としていた。1秒経路で調べると、14件のうち11件は復活ではなかった。主な原因は、共通タイムラインが2つのRoundを1つにまとめている区間だった。次の3つの規則を加えた（`rules/recorder_life.py`）。

1. 2つの死亡の間に新しいRoundの始まりが見えたら、復活ではなく、タイムラインのRound境界の見落としとして別の死亡に数える（`after_round_restart`）。始まりの手がかりは、購入カウントダウンの開始、戦闘の時計（1:40）の開始、得点の確定した増加の3つ。どれも時計や得点の読み取りから求め、Roundそのものはタイムラインのまま変えない。
2. 復活には、2つの死亡の間で味方の生存数が増えたことを求める。増えていないのに本人視点が長く続いたなら、1回目の死亡は誤検出なので、2回目の時刻に置き換える（`superseded`）。
3. 味方の生存数が0のときのHUDは、リプレイやRound終了画面なので本人視点に数えない。

| 指標 | 前回 | 今回 |
|---|---|---|

## 残る主な阻害要因

1. **移動（`movement_state`）とピーク（`peek` / `info_peek`）**：MOV-01/03、PEEK系、INFO-04。検出器はあるが精度が基準に届かない。視点の回転と移動を分けるには、キーフレーム直後の2フレームでは足りない。交戦区間だけを元の60fpsで連続して読み、複数フレームの動きと武器モデルの揺れを使う予定。
2. **武器（`weapon`）**：WPN-01。武器一覧の強調表示か、予備弾数の読み取りで特定する。予備弾数は持ち替えによる射撃の誤検出も防げる。
3. **味方のエントリー・セーブ判断・音声・状態異常**：それぞれ専用の検出器が必要。

## 範囲外にしたこと

- 共通タイムライン改善、Map認識、コード品質監査の担当範囲には手を入れていない。上記の検出は開発用の経路だけで使う。得点・タイマーは `DevelopmentGameTimeline` の観測行として渡せる形にしたが、タイムライン本体は変更していない。
- 正式Factは生成していない。特定試合の値に合わせた閾値調整もしていない（ポートレートの有無の閾値は、5試合を通じて空き枠と在席が大きく離れていることを確認して決めた）。
